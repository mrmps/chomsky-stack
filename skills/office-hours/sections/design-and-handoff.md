# Phase 5-6: Design Doc + Handoff

Read this file when the conversation, premise challenge, and alternatives are done. Execute it in full — do not summarize it from memory.

## Phase 5: Design Doc

Write the design document into the repo so it is versioned alongside the code it describes.

```bash
mkdir -p docs/design
DATE=$(date +%Y-%m-%d)
BRANCH=$(git rev-parse --abbrev-ref HEAD 2>/dev/null | tr '/' '-' || echo 'no-branch')
```

**Design lineage:** Before writing, check for an existing design doc covering the same feature:

```bash
ls -t docs/design/*.md 2>/dev/null
```

If a prior doc covers this same feature, the new doc gets a `Supersedes:` field referencing it. This creates a revision chain — you can trace how a design evolved across sessions.

Write to `docs/design/{date}-{feature-slug}.md`. Derive the feature slug from what is being designed (e.g. `2026-08-10-user-dashboard.md`).

After writing, tell the user: **"Design doc saved to: {path}. `plan-ceo-review` will pick it up automatically."**

## Design doc self-review

Before showing the doc to the user, read it back once and check:

- Does every section contain the user's actual answers, or did you paraphrase into generic language? Specifics beat summary.
- Is "The Assignment" a real-world action a person could do tomorrow, or is it "go build it"?
- Does the Recommended Approach match what the user actually chose in Phase 4?
- Are there claims in the doc the conversation did not support? Cut them.

Fix what fails, then present.

---

Present the design doc to the user via AskUserQuestion:
- **A)** Approve — mark Status: APPROVED and proceed to handoff
- **B)** Revise — specify which sections need changes (loop back and revise those sections)
- **C)** Start over — return to Phase 2

## Phase 6: Closing

Once the design doc is APPROVED, close the session. Keep it short. Two beats.

### Beat 1: Signal reflection

One paragraph. Reference specific things the user said and quote their words back to them. Do not characterize their behavior in the abstract.

**Show, don't tell:**
- GOOD: "You didn't say 'small businesses,' you said 'Sarah, the ops manager at a 50-person logistics company.' That specificity is rare."
- BAD: "You showed great specificity in identifying your target user."
- GOOD: "You pushed back when I challenged premise #2. Most people just agree."
- BAD: "You demonstrated conviction and independent thinking."

If the signal count from Phase 4.5 was high (3+, and they named a specific user or real demand evidence), say the honest version of what that means: this is the pattern of someone who ships. Say it once, plainly, without a pitch attached.

### Beat 2: The assignment

Restate the one concrete action from the design doc. One sentence. This is the last thing they read, so it should be the thing they do.

### Next step

Recommend one follow-on, in a single line — do not launch it yourself unless the user asks:

- Ambitious or under-scoped design → "Next: run `plan-ceo-review` to pressure-test the scope and find the 10-star version."
- Well-scoped design ready to build → "Next: start building. The design doc is at {path}."

The design doc in `docs/design/` is discoverable by `plan-ceo-review` — it reads it during its pre-review system audit.
